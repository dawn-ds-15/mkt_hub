## 1. Lưu KẾ HOẠCH theo TUẦN / THÁNG cho từng dự án — bắt buộc

### 1.1 Hiện trạng (verified 22/08)

| Điểm | Trạng thái |
|------|-----------|
| `POST /v1/leads-kpis/weekly` (`SaveWeeklyKpisDto`) | Chỉ nhận **actual**: `year, week?, month?, projectId?, rawLeads, mql, sql, oppCount, closedCount, opportunities[], closedDeals[]`. **Không có field plan** — gửi thêm `rawLeadsPlan`/`mqlPlan` → HTTP 200 `{success:true}` nhưng bị **strip im lặng**, dữ liệu không lưu |

Bằng chứng `planGoc` không phản ánh dự án (probe có JWT):

### 1.2 Yêu cầu nghiệp vụ

Form Kế hoạch nhập theo cặp **(Dự án + Tuần)** với dự án thường, hoặc **(Dự án + Tháng)** với Lead Generation — đối xứng với Form Thực tế hiện tại. Kế hoạch năm toàn hệ thống (`POST /plan`) giữ nguyên vai trò riêng, tách biệt hoàn toàn (đã xử lý phía FE theo BUG-L02).

### 1.3 Phương án A (khuyến nghị — mở rộng DTO `/weekly`)

```
POST /api/v1/leads-kpis/weekly
{
  "year": 2026,
  "week": 34,              // kỳ tuần (dự án thường)
  "month": 8,              // kỳ tháng (Lead Gen) — khi có month bỏ qua week (đã hỗ trợ)
  "projectId": "uuid",

  // NEW — field kế hoạch, optional, ≥ 0:
  "rawLeadsPlan":     100,
  "mqlPlan":          40,
  "sqlPlan":          20,
  "oppPlan":           5,
  "closedDealPlan":    2,

  // existing actual fields giữ nguyên...
}

201 → lưu bản ghi WeeklyKpi với cột PLAN riêng biệt cột ACTUAL
```

Hành vi bắt buộc:
1. Lưu plan vào bản ghi WeeklyKpi theo key `(year, week|month, projectId)` — tách biệt hoàn toàn giá trị actual.
2. Khi GET: nếu bản ghi của project+kỳ có plan đã lưu → `planGoc` trả **giá trị đã lưu** đó; nếu chưa có → fallback công thức phân bổ hiện tại (không phá hành vi cũ).
3. Validate `≥ 0`; khai báo đủ 5 field mới trong Swagger/docs-json.
4. Backward compatible: POST chỉ actual (không gửi plan) → 201, plan cũ không bị xoá/ghi đè.

### 1.4 Phương án B (nếu không muốn đụng `SaveWeeklyKpisDto`)

Endpoint riêng:

## 2. `POST /v1/expenses` — UPSERT HỎNG: trùng `(projectId, month, year)` → 500 (đÃ XÁC MINH 22/8/26)

### Kết quả test live trên BE production (22/8/26, token admin)

| Kịch bản | Kết quả |
|---|---|
| POST tạo mới (chưa có record cùng key) | ✅ 201 |
| POST lần 2 cùng `(projectId, month, year)` — ghi chú ngắn 50 ký tự | ❌ **500** `{"statusCode":500,"message":"Internal server error"}` |
| PATCH `/v1/expenses/{id}` theo id | ✅ 200 |

Kèm theo: khi note dài hơn ~100–150 ký tự, POST **tạo mới cũng 500** → nghi cột `directNotes` là varchar quá ngắn, cần chuyển sang `TEXT`. Cần check luôn `overheadNotes`.

### Yêu cầu kiểm tra & sửa

1. Sửa ngay lỗi 500 khi POST trùng key: hoặc upsert đúng (UPDATE record cũ), hoặc trả `409 Conflict` với message rõ ràng — không được để unhandled exception.
2. Theo thiết kế FE hiện tại (gộp nhiều dòng thành MỘT record theo kỳ): nếu giữ unique key `(projectId, month, year)` thì bắt buộc upsert ĐÚNG; nếu bỏ unique thì mỗi POST tạo record mới. **FE đã tự phòng ngừa** bằng cách tra cứu GET trước rồi PATCH nếu tồn tại — nhưng BE vẫn phải fix gốc.
3. Chuyển `directNotes`, `overheadNotes` sang kiểu TEXT (hoặc varchar ≥ 2000) — ghi chú tổng hợp đa dòng của FE dễ vượt 150 ký tự.
4. Trả error message có cấu trúc (`{statusCode, message, error}`) cho mọi validation/DB error thay vì 500 chung chung.

### Test case chấp nhận

- [ ] POST 2 lần cùng project + cùng tháng → lần 2 KHÔNG 500 (upsert đúng hoặc 409 rõ ràng)
- [ ] POST với directNotes 500+ ký tự → 201, GET trả đủ nội dung
- [ ] DELETE 1 dòng → dòng còn lại không bị ảnh hưởng

## 3. (Nhỏ) Xác nhận ý đồ công thức `planGoc` hiện tại

Không cần sửa gì ở mục này — chỉ cần ghi chú trả lời để FE đồng bộ hiển thị.
